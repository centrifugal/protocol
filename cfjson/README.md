# cfjson

> **For the Centrifugal ecosystem only.** This is not a general-purpose
> package. It is built for the needs of Centrifugal projects (Centrifugo,
> centrifuge, their SDKs and tools), supports what their schemas use and
> nothing more, and changes as they need it to: its API, the code it
> generates and its behaviour may change in any release, without notice
> and without a major version. Please do not depend on it outside of the
> Centrifugal ecosystem.

A code generator for JSON encoding and decoding of Go structs, and the small
runtime package the generated code is built on.

It was written to replace [easyjson](https://github.com/mailru/easyjson) (used
for encoding) and [segmentio/encoding](https://github.com/segmentio/encoding)
(used for decoding) in `github.com/centrifugal/protocol`, with two goals: the
same bytes on the wire and the same decoding semantics as before, and less CPU
for both directions.

The package depends on the standard library only.

## Usage

```
go run github.com/centrifugal/protocol/cfjson/cmd/cfjson \
    -raw Raw -out client.pb_cfjson.go client.pb.go
```

| Flag | Meaning |
| --- | --- |
| `-out` | Output file. Defaults to the first input file with the `_cfjson.go` suffix. |
| `-types` | Comma-separated structs to generate code for, together with the structs they refer to. All structs of the input files by default. |
| `-raw` | Comma-separated names of `[]byte` based types which hold an already encoded JSON value, the way `json.RawMessage` does (which needs no flag). `pkg.Type` for a type of another package. |
| `-append`, `-decode` | Names of the generated methods, `AppendJSON` and `DecodeJSON` by default. Unexported names keep them out of the package API. |
| `-fold-keys` | Match a key which is not the name of a field again without regard to the case of ASCII letters, like `encoding/json` does. Off by default. |
| `-no-nil-elements` | Decode `null` which is an element of a slice of pointers to structs, or a value of a map of them, as an empty struct and not as nil. Off by default, which is what `encoding/json` does. For code which would rather not meet nil there. |
| `-valid-raw` | Name of one more method to generate for the structs which have raw JSON values in them, however deep. It reports whether all of them are valid, which is all it takes for the struct to encode to valid JSON: everything else is written by generated code. Not generated by default. |
| `-runtime` | Import path of this package, for when it is moved or vendored. |

For every struct the generator writes two methods:

```go
// AppendJSON appends the JSON encoding of m to b.
func (m *T) AppendJSON(b []byte) []byte

// DecodeJSON decodes the JSON value at b[i] into m and returns the index after
// the value, or a negative number on error.
func (m *T) DecodeJSON(b []byte, i int, f cfjson.Flags) int
```

Encoding a value and decoding a whole document look like this:

```go
buf = msg.AppendJSON(buf[:0])

if n := msg.DecodeJSON(data, cfjson.SkipSpace(data, 0), 0); n < 0 {
	return cfjson.Error(data, n) // *cfjson.DecodeError with the offset.
}
```

When the input must be exactly one value, `cfjson.Unmarshal(data, &msg, 0)`
does the same and rejects anything which follows the value.

Besides what generated code calls, the package has a few functions which are
useful on their own: `Valid` checks that bytes are a JSON value, `AppendString`
and `UnmarshalString` turn a Go string into a JSON string and back.

`DecodeJSON` stops right after the value, the caller decides what may follow
it: nothing, whitespace, or the next value of a stream.

## What is supported

- `string`, `bool`, all integer types, `float32`, `float64`, and named types
  based on them;
- raw JSON: `json.RawMessage`, and the types listed in `-raw`;
- structs, by value or by pointer, of the same package and of other ones;
- embedded structs: their fields are fields of the struct they are embedded
  in, as `encoding/json` has it, in the same order and with the same rule
  for a name which comes more than once (the least nested field wins; of
  several that deep the one named by a tag, if it is the only one; otherwise
  the struct has no field of that name);
- types which have both `MarshalJSON` and `UnmarshalJSON`, like `time.Time`:
  the methods are called;
- pointers, slices and `map[string]T` of anything supported, nested as deep as
  needed;
- the `json` struct tag: the name, `omitempty` and `-`.

Anything else is an error at generation time which names the field: slices
of bytes (`encoding/json` writes them as base64), interfaces, arrays, maps
with keys other than strings, the `string` tag option, embedded types which
are not plain structs, types which encode themselves as text
(`MarshalText`, like `netip.Addr`), structs of other packages which have no
exported fields. A field left out or written in another way than
`encoding/json` writes it would be data lost without a word.

The JSON methods of a type are found wherever in the package they are
written, not only in the files given, and whoever wrote them: by hand or by
a tool like enumer. The exception is what easyjson generated, which is how
the type was encoded so far and not something it asks for. The generator reads
source files with `go/parser` and does not type check them, which keeps it
fast; packages the structs refer to are found with `go list` and read the
same way.

## Generating without touching the files with the types

Nothing has to be added to the file which declares a struct: no comment, no
tag, no method. What to generate is said on the command line, which can live
in a file of its own, and the result is one more file:

```go
// generate_cfjson.go
package jwtverify

//go:generate go run github.com/centrifugal/protocol/cfjson/cmd/cfjson -types ConnectTokenClaims,SubscribeTokenClaims -out claims_cfjson.go token_verifier_jwt.go
```

Only the types which are encoded and decoded directly are named. The
generator follows their fields and writes code for what they are made of:

- a struct of the same package gets the two methods, unless the package
  already has both of them for it, written by hand or generated in another
  run with another output file (one of the two is an error);
- a struct of another package cannot get methods, so it gets two functions in
  the generated file, `appendJSON<Package><Type>` and
  `decodeJSON<Package><Type>`, built from its exported fields;
- a type with JSON methods of its own is encoded and decoded by them. This is
  the slow path, one call through an interface and whatever the method
  allocates, but it is what keeps a type like `jwt.NumericDate` or
  `time.Time` meaning what its package says it means.

[internal/testtypes/foreign](internal/testtypes/foreign) is a package set up
this way, with tests which compare the generated code with `encoding/json`.

## Encoding semantics

The output is always valid JSON (RFC 8259), whatever the values are, as long
as raw values hold valid JSON themselves. Where easyjson produces valid JSON
the output is byte for byte the same:

- fields come in declaration order, `omitempty` drops empty strings, zero
  numbers, `false`, nil pointers and empty slices, maps and raw values; struct
  values are never dropped;
- a nil pointer, slice or map which is not dropped is `null`, an empty slice
  is `[]`, an empty map is `{}`, an empty raw value is `null`;
- strings are escaped like `encoding/json` does with HTML escaping on: `<`,
  `>`, `&`, U+2028 and U+2029 are escaped, invalid UTF-8 becomes `\ufffd`;
- raw newlines are dropped from raw values, since the protocols this was made
  for delimit messages with `\n`;
- floats use the shortest representation which round-trips (`'g'` format);
- map keys are written in iteration order, that is in random order.

One case where easyjson does not produce valid JSON is handled differently:
NaN and infinite floats are written as `null` rather than as `NaN` and `+Inf`.

Compared with `encoding/json` (v1, and v2 where it differs), the differences
are deliberate:

- map keys are not sorted (`encoding/json` sorts them);
- a nil slice or map is `null`, as in v1 (v2 writes `[]` and `{}`);
- HTML characters are escaped, as in v1 (v2 does not escape them);
- NaN and infinite floats are `null` (`encoding/json` returns an error);
- what a `MarshalJSON` method returns is written as it is, newlines dropped:
  it is not compacted and its strings are not HTML-escaped;
- a `MarshalJSON` which fails, or returns something which is not valid
  JSON, is reported as `encoding/json` reports it: `cfjson.Marshal(v)`
  returns a `*cfjson.MarshalerError`. Generated encoders append and have no
  error to return, so `AppendJSON` itself panics with that error, which is
  what `cfjson.Marshal` recovers. Encode values of types which have such
  methods anywhere in them with `cfjson.Marshal`; a type without them cannot
  fail to encode;
- a `MarshalJSON` with a pointer receiver is called for every value of the
  type, since generated encoders take values by pointer. `encoding/json`
  does not call it for a value it cannot take the address of, a value of a
  map, so a map of such values is an error at generation time.

## Decoding semantics

The input must be valid JSON as RFC 8259 defines it, which includes being
valid UTF-8. How values get into Go types follows `encoding/json`, except for
the two rules about keys, which are the ones `encoding/json/v2` has:

- unknown fields are skipped, after being checked for valid syntax;
- a key is matched to a field only if it is the name of the field exactly,
  letter case included. For input which has always been allowed to be
  written as `{"Channel": ...}`, such as requests to an HTTP API, the
  `-fold-keys` option brings the matching of `encoding/json` back: exact
  first, then without regard to case. It costs nothing for keys written the
  way fields are named, and a key still may not repeat in any spelling;
- a key may come once in an object: a repeated key of a field, or of a map,
  is an error. A parser which takes the first of two values and one which
  takes the last read different messages out of the same bytes, and the way
  to not be one of the two is to take neither. Inside of raw values and of
  skipped values keys are not looked at;
- `null` leaves a string, number, bool or struct untouched, and resets a
  pointer, slice or map to nil; a raw value gets the four bytes of `null`;
- a map is replaced by the decoded one (`encoding/json` adds to a map which
  is there already), a struct behind a pointer which is there already is
  decoded into;
- strings are unescaped, an escaped surrogate without its pair becomes
  U+FFFD;
- a number with a fraction or an exponent, or one which does not fit, is an
  error for an integer field;
- raw values and skipped values are checked as strictly as everything else,
  with one difference to `encoding/json`, which refuses any value nested
  deeper than 10000 levels: here only values of recursive types are limited
  (`MaxDepth`, 1024). A raw value may be nested as deep as its size allows,
  since nothing here recurses on it;
- `-fold-keys` folds the case of ASCII letters only (`encoding/json` also
  folds a few other letters, such as the Kelvin sign to `k`);
- everything decoded is a copy, strings and raw values alike: nothing points
  into the input, which may be reused as soon as decoding returns.

## Safety

Decoders are meant for untrusted input:

- they never read outside of the input, never modify it and never panic, which
  is fuzzed (see the `Fuzz*` functions here and in the packages using cfjson);
- skipping and validating values is iterative, so nesting in unknown fields
  and in raw values uses no stack, however deep it is;
- generated decoders recurse only as deep as the types nest. For types which
  can contain themselves the depth comes from the input, so it is limited to
  `cfjson.MaxDepth`, 1024 levels;
- everything is linear in the size of the input;
- no `unsafe`, in the package or in generated code: everything is ordinary
  bounds-checked Go.

How this is checked:

- fuzzing, of the package itself against `encoding/json` and of generated
  decoders against the decoder they replaced;
- `golangci-lint` with gosec, staticcheck, gocritic, errorlint and `go vet`
  with every analyser on, over the package and over generated code (see
  `.golangci.yml` in the repository root), plus `govulncheck` and CodeQL in CI;
- the tests also run where `int` is 32 bits (386) and where the byte order is
  big-endian (s390x), since strings are scanned a machine word at a time.

## Why it is fast

- Encoders append to a `[]byte` the caller owns. There is no writer object and
  no method call per token, and whether a comma is needed is known at
  generation time instead of being tracked at run time.
- Methods have pointer receivers. easyjson uses value receivers, which copies
  a struct every time it is encoded.
- Decoders take the input and an index and return the new index, with errors
  reported as a negative index. The whole decoder state lives in registers:
  there is no lexer struct to load from and store to on every token, and no
  error value to pass around on the happy path.
- A short string is written with the words which were loaded to check that
  it needs no escaping, two to four stores instead of a call to `memmove`.
- Encoders write fields in the order they are declared in, so a decoder first
  compares the input with the key the next field would have, as it is
  written: `"channel":`, quotes and colon included. That is a couple of word
  compares with a constant, and when it holds the key was never read as a
  key. Anything else (another order, a field left out, whitespace, an
  escape) is read as a key and looked up with a `switch`, which the compiler
  turns into a search by length and content without hashing or allocating.
- A map is filled with one hash operation per entry: whether a key came
  twice is told by counting the entries, not by asking the map before every
  store.
- The whole input is looked at once before decoding (`Prescan`). Most
  messages are printable ASCII without a single backslash, and knowing that
  up front means the end of a string is simply the next quote: no escape
  sequences, no control characters and no UTF-8 to check per string.
- Otherwise strings are scanned a machine word at a time (SWAR), long ones
  with `bytes.IndexByte`, which is vectorized in the Go runtime.
- No reflection anywhere, in either direction.

Go's SIMD packages (`simd`, `simd/archsimd`) are still behind
`GOEXPERIMENT=simd` as of Go 1.27, so a library cannot rely on them; the word
at a time code above needs nothing beyond plain Go. This has a price on amd64,
where segmentio has assembly using AVX2: checking a long run of bytes for
control characters is where pure Go is behind, which shows when validating a
message whose payload is one long string. See
[BENCHMARKS.md](BENCHMARKS.md) and [FOLLOWUPS.md](FOLLOWUPS.md).

See [BENCHMARKS.md](BENCHMARKS.md) for the numbers against easyjson and
segmentio, and [../internal/cfjsoncmp](../internal/cfjsoncmp) for the
benchmarks themselves and for the tests which prove compatibility with both.
[FOLLOWUPS.md](FOLLOWUPS.md) lists what else could be done in the projects
using this package.

## Moving to a module of its own

Nothing here knows about `centrifugal/protocol`. To move the package, copy the
directory, replace the import path in `cmd/cfjson/main.go`,
`gen/gen.go` (`DefaultRuntime`) and the tests, and regenerate.
