# cfjsoncmp

This module proves that the JSON code `github.com/centrifugal/protocol` has now
(generated by [cfjson](../../cfjson)) is compatible with, and faster than, the
code it had up to v0.22:

- encoding: methods generated by [easyjson](https://github.com/mailru/easyjson)
  writing into the custom writer from `encode_writer.go`;
- decoding and validation: [segmentio/encoding/json](https://github.com/segmentio/encoding).

It is a module of its own so that `protocol` does not depend on either
library. `go test ./...` in the repository root does not descend here, use
`make json-compat` and `make json-bench` there.

## What is in here

| File | What it is |
| --- | --- |
| `types.go` | The message structs of `client.pb.go` as of the migration, with everything but the type declarations removed. |
| `types_easyjson.go`, `encode_writer.go`, `raw.go` | The old encoding code, unchanged apart from the package name. |
| `types_cfjson.go` | cfjson code for the same structs, generated with the default (exported) method names. |
| `types_cfjson_fold.go` | The same generated with `-fold-keys`, under other method names: decoders which match keys without regard to letter case, as segmentio does by default. |
| `compat_test.go`, `diverge_test.go` | Tests and fuzz targets comparing the two on the same values and inputs. |
| `golden_test.go` | Keeps `../../testdata/json_golden.txt` equal to what easyjson produces. `protocol` tests its encoders against that file, without needing easyjson. |
| `bench_test.go` | Benchmarks of both on the same messages. |
| `results/` | Raw benchmark output the numbers below come from. |

Since both implementations are methods of the same struct types, a test
encodes the very same value with both, and decodes the same bytes into two
values which can be compared with `reflect.DeepEqual`.

`types.go` is a snapshot: the easyjson code cannot be regenerated here, so
messages added to the protocol later are not part of the comparison. The
generator they are produced with is: `types_cfjson.go` must always be the
output of the current generator (`TestGeneratedCodeIsUpToDate`).

## Compatibility

Encoding (`TestEncodeMatchesEasyjson` and friends): 200 000 random messages of
all 43 types, filled with strings that need escaping, invalid UTF-8, nil and
empty slices, maps and raw values, produce identical bytes.

Decoding (`TestDecodeMatchesSegmentio_*`, `FuzzDecodeMatchesSegmentio`): both
decoders must agree on whether an input is acceptable and on every field of
the result, including nil versus empty, and cfjson must not leave a string
pointing into the input. Inputs
are everything the encoders produce, a few hundred hand-written edge cases
decoded into every message type, and whatever the fuzzer comes up with.

Validation (`TestValidMatchesSegmentio`, `FuzzValidMatchesSegmentio`):
`cfjson.Valid` and segmentio's `Valid` agree on every input which is valid
UTF-8.

### Deliberate differences

The goal is compatibility with clients which send JSON, not with segmentio:
where segmentio departs from RFC 8259, cfjson follows the RFC. None of the
differences is reachable by a client which sends valid JSON as the protocol
describes it.

On decoding, cfjson is stricter in five ways:

- **Input which is not valid UTF-8 is rejected.** segmentio replaces invalid
  UTF-8 by U+FFFD in strings it decodes, and passes it through untouched in
  raw values such as the payload of a publication. A payload like that then
  goes out to subscribers, and a browser closes a WebSocket connection which
  receives a text frame that is not UTF-8. For the same reason `cfjson.Valid`
  rejects it, so an invalid payload coming from the application fails to
  encode rather than reaches clients.
- **Data after a message is rejected.** segmentio's `Parse` hands whatever
  follows the value back to the caller, and `protocol` ignored it:
  `{"id":1}garbage` was a valid command.
- **A key which comes twice in an object is rejected.** segmentio decodes
  both, so the last one wins, or the two are merged when the field is a
  message or a map.
- **Keys are matched exactly.** segmentio, like `encoding/json`, falls back
  to matching without regard to letter case: `{"ID":1}` set the field `id`.
  To cfjson it is a field the message does not have. (The tests here run
  segmentio with `DontMatchCaseInsensitiveStructFields`, so that everything
  else can still be compared value by value.)
- **Integers which overflow 64 bits are rejected.** segmentio misses most
  such overflows and stores a wrapped around value:
  `{"offset":21000000000000000000}` decodes to offset 2553255926290448384.

The second pair is there so that this parser and another one which has
looked at the same bytes (a proxy, a firewall, the client itself) cannot
disagree on what a message says.

On encoding there is no difference with easyjson for the protocol types. For
types with floats (there are none in the client protocol) NaN and infinities
are written as `null`, where easyjson writes `NaN` and `+Inf`, which is not
JSON.

The rest are details:

1. **Backspace and form feed in strings are written as `\u0008` and
   `\u000c`**, as the old writer of `protocol` did. This only matters for
   centrifuge, which used segmentio's `Escape` directly: that one writes `\b`
   and `\f`. centrifuge escapes with `cfjson.AppendString` now; either way a
   JSON parser reads the same string.
2. **Recursive types have a nesting limit.** `FilterNode` can contain
   `FilterNode`s. segmentio recurses as deep as the input goes, cfjson stops
   with an error past 1024 levels, so that a
   client cannot make a server use an arbitrary amount of stack.
3. **Strings are always copied.** The frame decoder of `protocol` used
   segmentio's zero-copy mode, which left plain ASCII strings pointing into
   the frame. cfjson has no such mode: nothing decoded shares memory with
   the input.

Things which look like candidates for a difference but are not, because
segmentio does the same and so does `encoding/json`: a top level `null` is an
empty message, an escaped surrogate without its pair becomes U+FFFD, a raw
value of `null` is kept as the bytes `null`.

## Performance

The numbers are in [cfjson/BENCHMARKS.md](../../cfjson/BENCHMARKS.md), which
is generated from the raw output in `results/`.

To add a machine, in the repository root:

```
make json-bench
mv internal/cfjsoncmp/bench.txt internal/cfjsoncmp/results/<machine>.txt
make json-bench-doc
```

`benchdoc.sh` explains the optional `<machine>.before.txt` and
`<machine>.after.txt` files with the benchmarks of `protocol` itself.
